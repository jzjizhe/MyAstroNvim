## New BLOCKERs introduced in Round 2

**BLOCKER 1 — §3.4 item 4's expiration rule kills the `nvim .` dashboard flow that §5.3 explicitly requires to keep working.**
§3.4 says: on `VimEnter`, if `vim.fn.argc() > 0` or any non-floating normal buffer is already named/modified/non-empty → set the flag and `return true` immediately. For `nvim .`, `vim.fn.argc()` is 1 (the directory sits in the arglist, passed through unchanged by the `~/.local/bin/nvim` wrapper's `exec "$L/bin/nvim" "$@"`), so the autocmd self-destructs at `VimEnter` before `snacks.dashboard.open()` can ever run — and the "named buffer" prong fires too (the startup buffer is named after the directory). §5.3 then requires: "verify `nvim .` opens dashboard beside Neo-tree and auto-deletes the autocmd", which is unreachable under this rule. The rule needs a directory carve-out, e.g. expire only when `argc() > 0` with a non-directory first argument (`not vim.fn.isdirectory(vim.fn.argv()[1])`), and the "named buffer" check must ignore the directory buffer pending neo-tree's `hijack_netrw_behavior = "open_default"` (`lua/plugins/user.lua:15`). Both prongs as written also fire for `nvim .`, so the fix must cover both.

**BLOCKER 2 — §1's acceptance criteria for `nvim-highlight-colors` contradict §3.1's own filetype allowlist on `.lua` files.**
§1 line 18 requires that opening `init.lua`/`README.md` loads **neither** of `nvim-ts-autotag` **nor `nvim-highlight-colors`**, and caps `init.lua` loads at ≤ 20. But §3.1 puts `"lua"` in `nvim-highlight-colors`'s `ft = { "css", "scss", "html", "lua", "json" }` — the lazy.nvim `ft` handler loads the plugin on any `FileType` match (`lazy/core/handler/ft.lua:12-23`), so opening `init.lua` (filetype `lua`) loads it by design, and `nvim-ts-autotag` remains off. Arithmetic: baseline 26 on `init.lua` − none-ls − mason-null-ls − todo-comments − ts-autotag (− blink.compat if it was in the lua-load set) leaves 21–22, above the ≤ 20 gate, with highlight-colors staying in the count. §5.1's own assertion ("remain unloaded on `README.md`") is consistent with the allowlist (markdown is excluded); only §1 is wrong. Either drop `"lua"` from the allowlist (sacrificing the stated hex-color-editing use case in `lua/winter_is_coming.lua`) or amend §1 to "nvim-highlight-colors loads only on css/scss/html/lua/json" and raise the `init.lua` threshold to ≤ 21.

**BLOCKER 3 — the user-side `opts.exclude_buffer` silently drops AstroNvim's large-buffer protection (§3.1).**
AstroNvim's spec ships `exclude_buffer = function(bufnr) ... return buf_utils.is_large(bufnr) or not buf_utils.is_valid(bufnr) end` (`astronvim/plugins/highlight-colors.lua:16-20`), guarding buffers above astrocore's `large_buf` limits (1.5 MB / 100k lines, `_astrocore.lua:36-40`). In lazy.nvim opts merging a function value replaces the inherited one (`util.lua:452-470` — `can_merge(function)` is false, value overrides), so the plan's `exclude_buffer = function(bufnr) return not color_fts[vim.bo[bufnr].filetype] end` removes the large-buffer/valid-buffer guard for allowlisted types — a large `.json` or `.lua` buffer then gets the full color-literal scan this iteration exists to eliminate. Compose the two guards instead: `color_fts[ft] and not require("astrocore.buffer").is_large(bufnr) and require("astrocore.buffer").is_valid(bufnr)`.

Non-blocking observations for the implementer: blink's doc-window `winhighlight` in §3.3 omits the default `EndOfBuffer:BlinkCmpDoc` member (cosmetic `~` fallback in the doc window); the `blink.cmp` kind-icon guard is only reachable via a `completion.menu.draw.components.kind_icon.{text,highlight}` opts override, since AstroNvim's `get_kind_icon` closure is spec-local and has no opts hook; §5.1's `values(...) == {}` check needs `vim.deep_equal` rather than `==`. These need no plan revision.
