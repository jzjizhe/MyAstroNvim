## BLOCKER 1 — `event = {}` is a no-op in the installed lazy.nvim; the ft-scoping of `nvim-ts-autotag` / `nvim-highlight-colors` will silently fail (plan §3.1 line 69 and §5 Risks line 143)

The plan's prescribed mitigation ("explicitly set `event = {}` when overriding `ft`") does not work in lazy.nvim v11.17.5. List-type loader fields (`event`, `ft`, `cmd`, `keys`) from every spec fragment of a plugin are concatenated by union, in fragment-chain order:

- `~/.local/share/nvim-fast/lazy/lazy.nvim/lua/lazy/core/plugin.lua:447-465` — `M._values` walks the fragment metatable chain (`super.__index`), accumulates earlier fragments' values into `ret`, then for list-type fields returns `Util.extend(ret, values)`.
- `~/.local/share/nvim-fast/lazy/lazy.nvim/lua/lazy/core/util.lua:338-349` — `M.extend` appends new unique values; `Util.extend({"User AstroFile"}, {})` returns `{"User AstroFile"}` unchanged.
- `~/.local/share/nvim-fast/lazy/AstroNvim/lua/astronvim/plugins/ts-autotag.lua:3` (`event = "User AstroFile"`) and `highlight-colors.lua:3` (`event = { "User AstroFile", "InsertEnter" }`) are earlier fragments of those plugins, and the user fragment in `lua/plugins/user.lua` merges on top of them.

Result: with `ft = {...}` + `event = {}`, both plugins keep their `User AstroFile` (and, for highlight-colors, `InsertEnter`) load triggers and still load on every file open. This silently defeats three of the plan's acceptance criteria: plugin count loaded on file open ≤ 19, cumulative load ≤ 185 ms, and the specific ts-autotag/highlight-colors savings (~9.5 ms) claimed in §2.1.

Working alternatives, verified against the same code paths:
- `event = false` — `Plugin.values` short-circuits on the falsy chain lookup (`plugin.lua:430-432`) and the handler is skipped entirely (`lua/lazy/core/handler/init.lua:101-107`, `if plugin[type] then`); `plugin.lazy` still resolves to true via `plugin.ft` (`plugin.lua:237-245`).
- `event = function() return {} end` — the function form receives the accumulated list and its return value replaces it (`plugin.lua:459-461`).

The plan's own diagnosis of the merge problem is correct; only the remedy needs updating to `event = false` (or the function form) for both plugins. The same union rule means `cmd = "HighlightColors"` and the `<Leader>uz` mapping survive correctly, and `ft` lists merge cleanly here since neither AstroNvim spec defines `ft`.

- Validation request: after the fix, run headless `nvim +'lua print(vim.inspect(require("lazy.core.config").plugins["nvim-ts-autotag"]._.loaded))' README.md` and the same for `nvim-highlight-colors` — both must be nil (unloaded) on a markdown/lua buffer, and `:HighlightColors` must still load highlight-colors on demand.

- Validation request: after implementing the `strip_italics` debounce (§3.4 item 2), open a file, let the `User LazyLoad` burst settle, then run `:lua local t={} for n,h in pairs(vim.api.nvim_get_hl(0,{})) do if h.italic or (h.cterm and h.cterm.italic) then t[#t+1]=n end end vim.print(t)`; repeat after a late lazy load (trigger which-key with `<Leader>`, blink.cmp with `i`). The list must be empty each time — the plan's wording "skip full scan on `User LazyLoad` unless a non-`winter-is-coming` theme is active" admits an implementation that starves scans of plugins defining italics after the theme loads.
